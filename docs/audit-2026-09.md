# Helm Terminals audit, September 2026

Branch `audit/2026-09`, based on `main` at `9226824`. Nothing here is deployed or pushed. Checked items are marked
**verified** (read in code, run in tests or measured); everything else is marked as an estimate or open question.
An audit narrows risk; it doesn't prove there are no vulnerabilities.

## 1. Architecture

| Part | What it is |
|---|---|
| `backend/app` | FastAPI API. Routes in `routes/`, business logic in `services/`, chain adapters in `chains/`, signers in `signing/`, SQLAlchemy models in `models.py` (tables created with `create_all`, no migrations). |
| `backend/helm_bot` | Telegram bot. A separate Railway service that calls the API with `BOT_API_KEY` and a per-user bot session. |
| `frontend/src` | React + Vite single-page app, served by `vite preview` on Railway. Session token kept in `sessionStorage` (per tab). |
| Signing | `SIGNER=turnkey` in production: keys live in Turnkey, and the DB stores only the key ID and address. The local signer (Fernet-encrypted keys in the DB) refuses `ENV=production`. |
| Chains | Solana (pump.fun via PumpPortal, LetsBonk, Bags, Meteora DBC and others), plus EVM Base, BNB Chain, Ethereum and Robinhood Chain (Clanker, Flap, Four.meme, Pons, Uniswap v2), with swaps through KyberSwap and cross-chain routing through Relay. |
| Money movement | Every spend is a two-step preflight/confirm. The server builds a preview and hashes it. The confirm must carry the same hash plus an idempotency key, and can carry a 2FA code. A `Job` runs in the API process (`run_job`) and records one `Transaction` per chain transaction. |
| Market view | DEX Screener (pools and metrics) plus GeckoTerminal (candles), server-side with caching (`services/market.py`). |

Tests: 168 backend tests (pytest, SQLite, faked RPCs and launchpads), all passing. The frontend type-checks and
builds.

## 2. Transaction speed

### How it was measured
`bench_tx.py` models the latency of the real `SolanaRPC` client and `Executor`. It replaces the network with a mock
where every RPC round trip costs 80 ms and a sent transaction confirms after a set landing time. Nothing touched
production or a real chain. The numbers show app-side waiting, not live latency.

**Verified path of one Solana trade:**
1. Balance before the trade.
2. Launchpad builds the transaction (a PumpPortal HTTP call).
3. Sign (Turnkey API).
4. `simulateTransaction`, then `sendTransaction`.
5. Poll `getSignatureStatuses` until confirmed.
6. Balance after, to record what was spent.

The UI then polls `GET /jobs/{id}`.

### Bottlenecks found and changes

| Bottleneck (verified in code) | Change | Before → after (model, 80 ms RTT) |
|---|---|---|
| Confirmation polled every **1.0 s** from the moment of sending (`chains/solana.py confirm`). The timeout counted only sleep time, not RPC time. Every poll searched full history. | Poll every 0.25 s for the first 8 s, then 1 s. The deadline is wall-clock. History is searched only on the final check. Brief RPC errors are ridden out (up to 5 in a row). | trade that lands in 0.6 s: **1.49 s → 1.07 s**. Lands in 1.2 s: **2.57 s → 1.73 s**. Lands in 2.5 s: **3.65 s → 3.06 s**. |
| Buy preview read each wallet's SOL balance one after another (`routes/launches.py trade`). | Read concurrently (8 at a time). | 5-wallet preview balance check: **0.41 s → 0.08 s**. It runs twice per trade: preview and confirm. |
| Balance-before read happened after the launchpad built the transaction. | Read while the launchpad builds it. | Saves about one round trip per wallet (not modelled). |
| UI polled the job every **1.5 s**. | 0.5 s for the first 10 s, then 1.5 s. | Up to about 1 s sooner on screen (estimate). |
| Parallel trades with many wallets would multiply the new poll rate. | The fast-poll interval scales with the wallet count, capped at 1 s: a 50-wallet batch stays at the old rate of about 1 call per second per wallet. | — |

**Not changed, on purpose:** simulation before every send, slippage limits, EVM nonce locking, idempotency keys, and
the 2FA gates. `sendTransaction` keeps `maxRetries: 3`: the node rebroadcasts the same signed transaction, with the
same signature, so this can't double-spend.

**Not measured:** Turnkey signing latency, PumpPortal and other launchpad build latency, live RPC latency. These
need timing in staging with real providers. The next step would be timing logs around each stage of `run_trade`.

### Transaction status accuracy (fixed)
- A transaction that was **sent but not confirmed in time** was recorded as **failed**. That's wrong (it may still
  land) and dangerous (it invites a retry, meaning a double buy or send). There is now an `unconfirmed` job status,
  and any error after sending (RPC outage, timeout) produces it instead of `failed`, on both Solana and EVM.
- A **timed-out Solana deploy** used to mark the launch failed and drop the mint. A retry would then create a second
  token. The launch now stays `deploying` with its mint. The workspace calls `POST /launches/{id}/recheck`, which
  marks it live when the mint exists. Only after the node says the account doesn't exist, 10 minutes on, is it
  marked failed.
- **Jobs orphaned by a restart** (jobs run inside the API process, so a Railway deploy kills them) used to leave the
  UI spinning forever. `GET /jobs` now reports `unconfirmed` with an explorer hint once a job has been quiet for
  15 minutes.
- The review dialog shows a "Submitted" state while waiting, a warning if the connection drops ("Don't confirm it
  again"), and a clear "Sent, not confirmed yet" result. It can be closed while waiting.
- **Open:** a timed-out **EVM** deploy still marks the launch failed, so the double-deploy risk remains there.
  Fixing it needs the token address read from the receipt later.

## 4. Revenue flow (verified in code; no rates, recipients or fund flows changed)

| Stream | Where | Collected how | Recorded in Helm? |
|---|---|---|---|
| Solana trade fee | `services/fees.py`, `executor.run_trade` | `PLATFORM_FEE_BPS` (0–5%) of the SOL side, added as a transfer **inside** the trade transaction, or sent right after if it doesn't fit. A failed trade never pays a fee. | **Yes**: a `FeeRecord` per wallet trade with basis, platform and referral lamports, and the signature. |
| Referral share | same | `REFERRAL_SHARE_BPS` (default 25%) of the fee, paid on-chain to the referrer's payout address. With no address it is **held by the platform and marked `owed`**. | Yes (`referral_status` none/paid/owed). **No payout process for owed amounts.** |
| EVM trades on a bonding curve | `routes/launches.py _trade_evm` | **No fee** ("none on bonding-curve trades"). | — |
| EVM trades routed through a DEX | `chains/kyber.py` | `feeAmount` bps taken by the KyberSwap router to `PLATFORM_FEE_WALLET_EVM`. | **No.** Only the preview mentions it. |
| USDC routing and bridge | `chains/relay.py` | `ROUTE_FEE_BPS` (default 0.3%) as a Relay `appFees` entry. It accrues at Relay and must be **claimed at relay.link**. | **No.** |
| Clanker LP rewards | `chains/clanker.py` | `CLANKER_PLATFORM_REWARD_BPS` share of the creator's LP rewards. It accrues in Clanker's fee locker and must be **claimed**. | **No.** |
| Bags partner share | `chains/bags.py` | Partner config; accrues to `BAGS_PARTNER_WALLET`, claimed on Bags. | **No.** |
| Deploys, withdrawals, disperse, claims | — | No platform fee. | — |

**Gaps:**
- Only the Solana trade fee is recorded. Kyber, Relay, Clanker and Bags revenue exists only on-chain or in partner
  dashboards, so there is no single revenue number.
- Owed referral amounts have no payout process.
- There is no admin revenue view and no reconciliation.

**Costs that reduce net revenue:**
- Solana and EVM network fees (paid by user wallets, except platform transfers).
- Turnkey per-signature pricing (not checked here).
- RPC plans (Helius and others).
- A market-data plan (section 5).
- Railway.

**Recommendations (not implemented; each needs your approval):**
1. **One ledger.** Extend `FeeRecord`, or add a `revenue_events` table, with `source` (sol_trade, kyber, relay_route,
   clanker, bags) and `network`. Record Kyber's fee from the quote and receipt, and Relay's `fees.app` from the
   executed quote.
2. **Reconciliation job.** Daily: sum recorded fees per network and compare them with inflows to
   `PLATFORM_FEE_WALLET` / `_EVM`. On Solana, `getSignaturesForAddress` plus the transactions. Also read claimable
   Clanker, Relay and Bags balances.
3. **Admin revenue page.** Collected vs owed vs claimable, per stream and network.
4. **Owed referral payouts.** A batched payout job that an admin approves.
5. **Pricing (decision for you).** EVM bonding-curve trades earn nothing today. A follow-up fee transfer, as on
   Solana, would close that gap. It changes what users pay, so it needs sign-off and must show in every preview.

## 5. Chart data providers (researched 2026-09-27 from official pages)

**What Helm uses today:**
- DEX Screener `token-pairs/v1` for pools and metrics: 300 req/min, "commercial … purposes" allowed, with a clause
  against products whose *primary purpose* competes with DEX Screener. There's no OHLCV and no official embed.
- GeckoTerminal public API for candles: "v2-beta", about 10 calls/min, 1-minute cache, **no commercial terms
  published for keyless use**. Both cover Robinhood Chain (`robinhood`, checked live).

**Licensing gap:**
- The keyless GeckoTerminal API shouldn't be treated as licensed for a commercial app.
- CoinGecko's paid API (the same onchain data) requires "Powered by CoinGecko" attribution. It forbids
  "re-distribute or syndicate" without an executed agreement, and it lists a "Commercial redistribution license"
  only under Enterprise.
- Whether showing candles to Helm users counts as redistribution is **unclear. Ask CoinGecko in writing.**

| Provider | OHLCV | Robinhood | Cheapest commercial | Notes |
|---|---|---|---|---|
| CoinGecko API (onchain) | pool OHLCV | yes | Basic ≈$35/mo (labelled "personal use" but licence row says Commercial); Analyst ≈$129/mo | attribution required; redistribution unclear |
| DexPaprika | pool OHLCV | **not confirmed** | free tier states "Commercial use: Permitted" | no attribution required; 15–30 req/min free |
| Codex | `getBars` | yes (official page) | Growth from $350/mo | terms not read |
| Bitquery | OHLCV (GraphQL) | yes | Pro $99/mo ($79 yearly) | commercial licence from Pro |
| Mobula | token and market OHLCV | yes | Start-up $50/mo | commercial terms not stated |
| Birdeye / Moralis | OHLCV | not listed | $39–149/mo | terms not read |

**Recommendation:**
- Keep DEX Screener for pools.
- For candles, either put GeckoTerminal on a paid CoinGecko plan (after a written answer on redistribution), or use
  Bitquery Pro or Mobula (both document Robinhood Chain).
- DexPaprika is the cheapest clearly-licensed option if it covers Robinhood Chain.
- `services/market.py` already isolates the provider. Adding a `CandleProvider` interface with a primary and a
  fallback (for example CoinGecko, then Bitquery) is a small change.

If Helm moves from its own SVG chart to TradingView Lightweight Charts: it's Apache 2.0 with a NOTICE and
link-back requirement (its `attributionLogo` covers the link).

## 6. Security findings

The review was independent: a separate reviewer that didn't write the fixes, with proof-of-concept tests against
local copies only. No production system, credential or wallet was touched.

| # | Finding | Severity | Status |
|---|---|---|---|
| H1 | `/wallets/fund` could send to a watch-only address (any address the user typed) with no 2FA. A stolen web session or a leaked bot key could empty wallets. | High | **Fixed.** Funding a watch-only target is kind `fund_external`, which always needs 2FA. `withdraw`, `send_tokens` and `fund_external` now need 2FA whatever `TFA_REQUIRED_KINDS` says. Test: `test_funding_a_watch_only_address_needs_2fa`. |
| H2 | Importing a key the attacker holds made it a "managed" wallet. Disperse, consolidate and bridge then moved funds there with no 2FA. | High | **Fixed.** Import now needs the web app (not the bot), the password, and the 2FA code when 2FA is on. Test: `test_importing_a_wallet_needs_…`. |
| M1 | A stolen session could turn on 2FA with the attacker's own authenticator, then withdraw. | Medium | **Fixed.** Setup requires the password. |
| M2 | No login or 2FA attempt limits; a 2FA code could be reused. | Medium | **Fixed.** A code works once per user (`totp_uses`). Wrong passwords are limited per email per client (10 per 15 min) and per email overall (100). Wrong codes: 8 per user per 15 min. |
| N1 | (from the first fix) Locking out by email alone let anyone lock a victim out. | Medium | **Mitigated.** Per email per client, plus a high per-email cap. Fully fixing it needs a captcha or trusted client IPs. |
| M3 | Helm signs whatever Relay, PumpPortal and Kyber return. The only check is a successful simulation. A compromised provider could drain the wallets that trade or route. | Medium | **Open. Recommendation:** allowlist Relay and Kyber contracts per chain; check `value` and approvals against the preview; allowlist Solana programs; compare simulated balance changes with the preview. |
| M4 | Defaults fail open: `SECRET_KEY` defaults to a public constant. | Medium | **Partly fixed.** With `ENV=production` the app won't start on the default or an empty key. If `ENV` is unset it still runs in development mode. Make sure the API service has `ENV=production` (set during the Turnkey switch; worth confirming). |
| M5 | Unlimited sign-ups each create Turnkey keys, and wallet creation had no cap. | Medium | **Partly fixed**: 500 wallets per account. **Open:** rate-limit sign-up per IP and verify email before creating keys. |
| L1 | The bot key acts as a master key for linked users. The bot's buy cap covers only `/trade`, not deploy, disperse or bridge. | Low | **Open.** Allowlist the endpoints bot sessions may call. |
| L2 | Sign-out didn't revoke the session on the server. | Low | **Fixed** (`/auth/logout`). |
| L3 | 422 responses echoed submitted values back, including a private key sent as an array. | Low | **Fixed** (the validation handler drops the values). |
| L4 | Metadata fetch SSRF check: 100.64/10 wasn't blocked; the DNS check and the connection are separate lookups. | Low | **Partly fixed** (`is_global`). The DNS rebinding window is still open. |
| L5 | Uploaded images weren't checked; no security headers. | Low | **Fixed.** Image type checked by content; `nosniff`, `X-Frame-Options`, `Referrer-Policy`; CSP on public images. |
| L6 | Self-referral; `/auth/register` reveals whether an email exists. | Low | Open. |
| N2 | Changing `SECRET_KEY` makes stored 2FA secrets unreadable. | Medium (operational) | 2FA now fails with a clear 503 instead of a 500. **Never rotate `SECRET_KEY` without re-encrypting `users.totp_secret_enc`.** |
| N4 | A 2FA code is used up at confirm even if the action then fails. | Low / UX | Accepted. After logging in, a withdrawal may need the next code (≤30 s). |
| Info | Dependencies: `pip-audit` found only build tools (pip, setuptools). `npm audit` found 2 moderate react-router advisories that don't apply here (SSR-only, and an open redirect with no user-controlled targets). Requirements are unpinned (`>=`); pin them with a lockfile. | Info | Open. |
| Info | Jobs and the automation budget lock live in the API process: a restart kills jobs, and several replicas would each have their own lock. | Info | Restart case mitigated (section 2). Run a single replica, or move jobs to a queue. |
| Info | The frontend is served by `vite preview`, which is not a hardened production server. | Info | Open: serve `dist/` from a static host or nginx with CSP. |

A test-isolation problem also turned up and was fixed: tests were reaching public EVM RPCs (main wallets' balance
reads), which made results network-dependent. EVM RPC calls in tests now fail fast offline.
